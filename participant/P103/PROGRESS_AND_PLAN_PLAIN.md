## 2. 已经做了哪些事，为什么有用

### A 阶段：先把训练和测分过程做可靠

我们修正了训练中的几个衔接问题：每回合如何重置、随机种子怎样传递、最后一步观测怎样保存，以及如何告诉 PPO“这是时间到了”。这类似检查机器人项目里传感器、控制器和电机之间的接线；程序能运行，并不保证数据接得正确。

随后建立了两套各有 100 个不同场景的题目。一套叫开发 v2，用来平时比较；另一套叫 A4 最终确认集，等最终候选确定后才评分。每个场景重复两次，所以每套运行 200 回合，但仍只有 100 道不同的题。A4 已建好并核对文件，尚未运行模型评分。

我们还用 v2 给旧模型重新建立了比较基准：模板 E001 为 51.67，E008 为 114.80，E009 为 125.33。E009 在旧 v1 得 108.33、公开题得 200.00，都是同一个模型做不同题的结果，不能说它因此自己涨分或降分。

E009 已有一份独立本地压缩备份，但那是较早的归档。之后 B—D 的成果需要另外保存。

### B 阶段：同一种训练做三次，看看是不是碰巧成功

我们用同一训练程序、同一预算和参数，只换三个随机种子，完成 E011、E012、E013。随机种子会影响网络初始状态和训练过程；换种子重练，就像让同一种学习方法从三个不同起点再走一遍。

每次训练在约 31 万、63 万、104 万样本处保存模型，并保存同一时刻的归一化统计量。这个中途存档叫“检查点”。三个最终分数分别是 121.40、124.40、126.67，平均 124.16，差距较小，因此有理由继续改进这套训练方法。

E009 是修正训练程序之前得到的，E011–E013 用的是修正后程序。因此可以比较同一套题上的成绩，但不能说三次新训练是完全照旧 E009 重做。

### C 阶段：训练时同时练基础题和协作题

E014、E015、E016 使用同样的三个种子。四路训练场景中，两路练基础任务，两路练协作任务；网络大小、训练预算等主要设置保持一致。

最终三次分数为 123.67、132.80、135.67，平均 130.71，比 B 阶段平均高 6.56，而且三个种子分别比较都提高了。所以，之后继续训练时，优先保留“一半基础、一半协作”的设置。

不过，平均分提高后仍发现一些具体问题：某些机器人漏掉目标，某些协作场景中两台机器人会连续碰撞。接下来我们从轨迹找原因。

### D 阶段：针对失败动作做改进，再试少量训练参数

先固定已经训练好的三个 C 模型，分别试了两条规则：

- **目标朝向**：看得见目标时，把原动作的 40% 换成朝最近目标的方向。
- **队友避让**：附近看得见队友时，给动作加一点远离队友的分量。

目标朝向在 v2 平均加 6.67 分。我们又建立全新的开发 v3，在另外 100 个场景上测，平均仍加 7.04 分。这比只修好某一条失败轨迹更有说服力。v3 现在已经用来比较方法，因此也属于开发题，不能再称为没见过的最后确认题。

避让确实减少了碰撞，但可能绕路、错过覆盖。把目标朝向和避让组合后，相对目标单项，v2 平均少 0.96 分，v3 平均多 0.76 分。所以目前不能说“组合一定更强”。

之后按预定顺序调学习率和探索系数，共完成 E017–E028 的 12 次训练。高学习率在短训练平均多 5.18 分，但完整训练只多 1.00 分，没有达到事先定好的“平均至少多 5 分才继续投入”门槛，因此停止。这表明本轮调参收益有限，不表示神经网络再也无法进步。

详细证据分别在 [B3_B4_REPORT.md](B3_B4_REPORT.md)、[C_REPORT.md](C_REPORT.md)、[D_TRAJECTORY_FOLLOWUP.md](D_TRAJECTORY_FOLLOWUP.md) 和 [D_PARAMETER_REPORT.md](D_PARAMETER_REPORT.md)。

## 3. E016 为什么明明朝目标走，反而少覆盖一步

原动作在纵向已经给了 −1.000，接近这个方向允许的最大力度。目标朝向规则混入的是长度为 1 的方向向量；它的纵向分量未必也是 −1。混合后纵向动作变成约 −0.941，推进变弱了。

原策略在第 5 步离目标 0.145661，修改后离目标 0.152852。覆盖半径恰好是 0.15，因此原策略已经覆盖到，修改后还差一点，要等下一步。这就解释了那一局为何少算一个目标步。

这里最值得学的是：**朝向更接近目标，并不保证到达更快。**动作幅度、当前速度和运动过程同样会影响结果。它和真实机器人控制中“方向对了，但速度不合适”的问题很接近。

这个问题已解释清楚，但新修正方案还没有实现。后面最多再试一轮小改动，不需要为此重写整个训练系统。

### 第二步：补齐旧模型和候选的公平比较

用 E009 跑一次开发 v3，给结果分配新目录。再和 E015 两个候选比较相同场景的分数、覆盖率及碰撞。已有结果如果对应的文件指纹没有改变，可以复用，不必为了“再跑一次”反复计算。

比较时看同一道题新旧版本差多少，再汇总全部题。不要拿 E009 的公开 200 分和候选的 v3 145 分比较，那是两套题。

同时开始准备 Linux 环境。我们目前主要在 Windows 上得到成绩，提前检查比赛平台可以给依赖、路径和时限问题留出处理时间。

### 第三步：有时间才做一轮“不要把好动作改弱”的实验

只提出一个具体想法：原动作已经明显朝目标走时不干预，原动作偏离目标时才用原来的 40% 目标混合。如何判定“明显朝向”，先写定规则，再开始实验。

固定原来的三份模型，只改这一项。先检查已知失败轨迹是否改善，再用完整 v2/v3 检查有没有在别的场景变差。建议平均至少多 3 分、至少两份模型改善且分组没有明显退化，才继续考虑；详细门槛必须在运行前定好，3 分只是判断是否值得投入的标准。

如果没有达到门槛，就结束这轮，继续使用已有候选。最晚 9 月 30 日结束新方法实验，不反复围绕某道题微调到满意为止。

### 第四步：选定一个候选，最后才拿出 A4

先根据开发结果选定一个候选，把模型文件、入口代码、动作参数和推理依赖固定下来。再提前写好“什么结果下换掉 E009”的规则，随后让候选和 E009 做同一套 A4 题。

建议采用保守规则：新候选比 E009 至少高 5 分、按场景估计的分差范围支持正向改善、两组没有明显退化，而且所有回合都运行成功。详细条件见技术版 F1。这些规则现在是建议，必须在看到 A4 分数前定稿。

如果 A4 结果不清楚，就保留 E009。若看完 A4 后又继续按它调模型，就相当于看过“期末卷”后再练题；必须如实说明它已参与开发，不能继续宣传为完全陌生的验证。

### 第五步：把实验候选变成真正可提交的文件

如果最后选择“网络＋动作修正”，仅复制 policy.npz 是不够的。比赛入口还要真正运行目标朝向和避让代码，否则交出去的模型行为和实验测到的不一样。

需要一起核对模型、归一化统计量、入口、依赖和 submission.yaml 中的文件指纹。还要用相同观测比较“最终提交入口”和“实验候选”的动作是否一致。

训练网络导出成 NumPy 时，应该和原网络动作一致；之后加入规则，最终动作本来就会改变。这是两层不同的检查，不要混在一起。

最后在干净的官方依赖环境以及 Linux 上运行预检和公开评测，检查时间、内存和回合是否完整结束。自己在 Linux 跑通仍是自测，官方成绩要等组织方核验。

### 第六步：整理报告，再按窗口公开提交

把报告开头、模型说明、复现命令和提交清单统一成最后选择的版本。旧 REPORT.md 仍以 E009 为主体，E011 的示例输出目录也早已使用，最终整理时要修正，避免别人照着运行就撞到旧目录。

如果保留 E009，要说明它由较早的训练程序生成；现在修正后的程序用相同参数重练，不保证得到原来的权重。复现“现有模型怎样推理”和“重新训练一个模型”是两回事。

然后按官方窗口把 P103 推到真正的 Fork，并创建 `[P103] Final Submission` PR，记录链接、提交时间、代码版本和模型指纹。不要等截止前最后几分钟才处理网络问题。

## 7. 现在最值得学的几个词

| 术语 | 简单解释 | 本项目中的用法 |
| --- | --- | --- |
| 基线 | 用来比较的旧方法或旧模型 | E009 是回退模型；C 的混合设置是继续训练的起点 |
| 随机种子 | 控制随机过程起点的数字 | 用 7101、7102、7103 观察同一种方法是否稳定 |
| 检查点 | 训练中途存档 | 网络和同一时刻的归一化统计量一起保存 |
| 归一化 | 按模型熟悉的尺度转换输入 | 均值、方差配错，即使权重对了，动作也可能不对 |
| 单因素实验 | 一次只改变一个明确因素 | 改学习率时固定网络、预算和场景；改动作规则时固定权重 |
| 配对比较 | 新旧模型做同一道题，比较这一题的差值 | 可减少题目本身难易差别对判断的干扰 |
| 区间估计 | 用一段范围表示当前数据的不确定性 | 分差范围包含 0，表示这些数据仍允许“没有提高”的解释；不是未来比赛的保分承诺 |
| 选择偏差 | 反复挑最适合已看过题目的模型，容易高估新题表现 | v2/v3 用于开发，A4 留到最后 |
| 哈希 / SHA-256 | 文件内容的指纹 | 确认被评测、被备份和被提交的是同一份文件 |
| local_preview | 本机跑出的预览结果 | 已完成的这些分数都属于这一类 |
| Git 提交、推送、PR | 本地存版本、上传到远程、向官方请求接收版本 | 三个动作各自有完成状态，不能互相替代 |

利用你已有的机器人经验，下一步重点学会解释动作和运动之间的关系，再把解释变成一次只改一个因素的实验。每次记录三句话：想验证什么、改变了什么、结果支持什么。这样既能推进比赛，也能建立可复用的开发方法。
